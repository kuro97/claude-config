## Шаг 0: Определение режима и флагов

### Режим

Проанализируй аргументы и определи режим:

**Если пользователь указал режим явно** (quick/standard/deep/ultradeep) — используй его.

**Если не указал** — определи автоматически по теме и спроси:

| Сигнал | Режим | Почему |
|--------|-------|--------|
| "быстро посмотри", "что такое", "кратко" | Quick | Простой вопрос |
| Обычный вопрос без явных маркеров | Standard | По умолчанию |
| Сравнение для принятия решения, выбор технологии | Deep | Влияет на архитектуру/бюджет |
| "максимально", стратегическое решение, смена стека | UltraDeep | Высокая цена ошибки |

### Флаги (перебивают дефолты режима)

| Флаг | Значения | Дефолт | Что делает |

## Фаза 1: SCOPE — Определение границ

- Сформулируй исследовательский вопрос в одном предложении
- Определи: что ВХОДИТ в исследование, что НЕ входит
- Целевая аудитория отчёта (CTO / разработчик / бизнес)
- Временной фокус (последний год / 2 года / без ограничений)
- **Критерии выбора решения** (3–7 штук) — по ним потом строится матрица в фазе SOLUTIONS.
  Типовые: стоимость владения, порог входа, совместимость со стеком, self-host возможен, зрелость/поддержка, лицензия, скорость внедрения
- **Есть ли шанс, что задача уже решена?** Почти всегда да → фаза SOLUTIONS обязательна. Явно выключается только `--solutions=0` (чистая теория, обзор рынка без внедрения)

## Фаза 3: RETRIEVE — Поиск информации

### Шаг 0: Определи стратегию поиска по типу темы

| Тип темы | Сигналы | Приоритетные источники | Паттерны запросов |
|----------|---------|----------------------|-------------------|
| Технология / инструмент | "что такое X", "как работает X" | docs, GitHub README, changelogs, release notes | `X documentation`, `X getting started`, `X vs alternatives` |
| Сравнение X vs Y | "сравни", "что лучше", "выбрать между" | бенчмарки, Reddit, HN, case studies, миграции | `X vs Y benchmark 2026`, `migrate from X to Y`, `X vs Y reddit` |
| Архитектура / паттерн | "как спроектировать", "архитектура для" | conference talks, блоги CTO, ThoughtWorks Radar, Martin Fowler | `X architecture pattern`, `X at scale`, `X production experience` |
| Безопасность | "уязвимости", "безопасность", "CVE" | NVD/CVE databases, OWASP, security advisories, GitHub Security | `X CVE`, `X security vulnerability`, `X OWASP` |
| Рынок / бизнес | "рынок", "конкуренты", "стоимость", "pricing" | аналитические отчёты, Crunchbase, Product Hunt, новости | `X market share`, `X pricing 2026`, `X competitors`, `X revenue` |
| Интеграция / API | "подключить", "интеграция", "API" | docs API, SDK, GitHub examples, Stack Overflow | `X API reference`, `X SDK example`, `X integration tutorial` |
| Готовое решение под задачу | "чем сделать", "есть ли готовое", "не писать самому" | GitHub, awesome-листы, Product Hunt, альтернативы-каталоги | `X open source`, `awesome X`, `X alternative`, `self-hosted X` |

Определи тип темы → используй соответствующие паттерны запросов для субагентов.
Если тема смешанная — комбинируй стратегии.

### Шаг 1: Языковой роутинг

Англоязычный поиск даёт консенсус, а не полноту. Практика эксплуатации, цены, «как это ломается в реальности» часто живут только в национальных сообществах.

**Пул языков и где искать:**

| Язык | Платформы | Что там сильнее всего |
|------|-----------|----------------------|
| `en` | официальные docs, GitHub, Hacker News, Reddit, Stack Overflow, arXiv | база по любой теме, релизы, англоязычный консенсус |
| `zh` | 知乎 (Zhihu), CSDN, 掘金 (Juejin), InfoQ CN, Gitee, 博客园 | инфраструктура, БД, ML/LLM, распределённые системы, дешёвый хостинг, обход лимитов |
| `ru` | Habr, vc.ru, dev-Telegram-каналы | практика в СНГ, локальные интеграции и платёжки, Yandex/1C-стек, обход санкционных ограничений |
| `ja` | Qiita, Zenn, Hatena Blog | надёжность и эксплуатация, embedded, аккуратные разборы edge-cases |
| `de` | heise, Golem, dev-блоги, c't | GDPR/правовое, промышленность, self-hosted, критика вендоров |
| `ko` | Velog, Naver D2, Kakao/Line Tech blogs | high-load, gaming, мобильное, real-time |
| `es` / `pt` | Medium-локали, dev.to-локали, форумы | fintech LatAm, дешёвая инфраструктура, аутсорс-практика |
| `fr` | LinuxFr, blogs, Développez.com | privacy, госсектор, OSS-политика |
| `hi` / `tr` | Medium, YouTube-разборы, форумы | аутсорс-практика, low-cost внедрения, рынок |

**Включение по режиму:**

| Режим | Языки |
|-------|-------|
| Quick | `en` + `ru` |
| Standard | ядро: `en` + `ru` + `zh` |
| Deep | **весь пул** |
| UltraDeep | **весь пул** + языки, специфичные для темы (страна-родина технологии, крупнейший рынок) |

`--lang=all` форсит весь пул на любом режиме. `--lang=core` — только `en+ru+zh`. Можно задать список явно: `--lang=en,zh,ja`.

**Как переводить запрос — правило:**

Переводится **смысл и нативная терминология**, а не слова. Буквальный перевод даёт мусор или англоязычные же результаты.

| Плохо (буквально) | Хорошо (нативно) |
|---|---|
| `observability 中文` | `可观测性 实践` |
| `queue best practices 日本語` | `メッセージキュー 運用 落とし穴` |
| `how to migrate по-русски` | `опыт миграции на X: грабли` |

Если не уверен в термине — сначала найди, как технология называется на этом языке (у многих есть устоявшийся перевод и аббревиатура), потом ищи им.

**Обязательно фиксируй:** какие языки реально запустил, какие пропустил и почему → в reach-метрику (фаза 4, Шаг 5).

### Шаг 2: Quick — последовательный поиск

3–5 запросов WebSearch последовательно по паттернам выбранной стратегии, из них минимум 1 — не на английском. Без субагентов.

### Шаг 3: Standard+ — Agent Reach: матрица субагентов

Субагенты запускаются **одним сообщением** через Agent tool (все параллельно). Агент — это `researcher` (Sonnet, read-only) либо `general-purpose`, если нужен доступ к Bash/Read для source-dive.

**Матрица «направление × языковой кластер»** — не плоские 5 направлений, а покрытие двумя осями:

| # | Направление | Режимы | Языки | Описание |
|---|-------------|--------|-------|----------|
| 1 | Основа | Standard+ | `en` | Официальная документация, определения, главные факты |
| 2 | Альтернативы | Standard+ | `en` | Конкуренты, сравнения, "X vs Y" |
| 3 | Проблемы | Standard+ | `en` + `ru` | Баги, ограничения, негативный опыт, подводные камни |
| 4 | Готовые решения | Standard+ | `en` | Shortlist OSS/SaaS/кейсов → передаётся в фазу 4 |
| 5 | Практика | Deep+ | `ru` + `zh` | Case studies, миграции, отзывы эксплуатации |
| 6 | Глубина | UltraDeep | `en` | Бенчмарки, академические источники, тренды, прогнозы |
| 7 | Локальный кластер A | Deep+ | `zh` | То же, что 1–3, но нативными терминами на китайском |
| 8 | Локальный кластер B | Deep+ | `ja` + `ko` | То же на японском/корейском |
| 9 | Локальный кластер C | UltraDeep | `de` + `fr` | Правовое, self-hosted, критика вендоров |
| 10 | Локальный кластер D | UltraDeep | `es` + `pt` + `hi` + `tr` | Рынок, low-cost внедрения |

**Кэп параллельных агентов:**

| Режим | Агентов за раз |
|-------|---------------|
| Standard | 4–5 |
| Deep | 8–10 |
| UltraDeep | 12–16 |

Больше 20 параллельных агентов — никогда без явной просьбы пользователя (глобальное правило).

### Шаг 4: Каскад «разведчик → глубокий читатель»

Сниппет выдачи — не источник. Он даёт заголовок и обещание, а факты, цифры и оговорки живут в тексте.

**Уровень 1 — разведчик** (агенты из матрицы выше):
- 3–5 запросов WebSearch по своему направлению и языку
- Возвращает список URL с заголовками, датами, типом источника и оценкой «стоит ли читать целиком» (1–3)
- **Не** пересказывает содержимое по сниппетам

**Уровень 2 — глубокий читатель** (Deep+, запускается после разведчиков):
- Берёт 2–3 источника с оценкой 3 из каждого направления
- Читает их **целиком через WebFetch**
- Извлекает: конкретные цифры, версии, условия воспроизведения, оговорки автора, что автор сам признал слабым
- Возвращает факты с прямой атрибуцией

На Standard уровень 2 применяется только к направлениям 1 и 4 (Основа и Готовые решения) — чтобы не раздувать стоимость.

### Промпт для агента-разведчика

```
Ты — исследователь-разведчик. Тема: {тема}. Направление: {направление}.
Язык поиска: {язык} — ищи НАТИВНОЙ терминологией этого языка, не переводи запрос буквально.
Платформы приоритета: {платформы для этого языка}.
Временной фокус: {временной_фокус}.

Задача:
1. Сделай 3-5 запросов WebSearch по своему направлению на своём языке
2. НЕ пересказывай содержимое по сниппетам — верни карту источников

Формат ответа — СТРОГО:

### Источник 1
- URL: [ссылка]
- Язык: [код языка]
- Тип: [docs / блог / форум / GitHub / paper / news / product]
- Дата: [дата публикации или "неизвестно"]
- Заголовок: [оригинал + перевод на русский]
- О чём: [1 строка по сниппету]
- Читать целиком: [1 = не стоит / 2 = возможно / 3 = обязательно] — почему

### Источник 2
...

В конце:

- Найдено источников: [N], из них "читать целиком = 3": [M]
- Запросы, которые я сделал: [список дословно]
- Главная гипотеза: [1-2 предложения]
- Пробелы: [что НЕ удалось найти на этом языке]
```

### Промпт для агента-глубокого-читателя

```
Ты — глубокий читатель. Тема: {тема}.
Тебе дан список URL: {список}.

Задача:
1. Прочитай КАЖДЫЙ через WebFetch целиком
2. Вытащи конкретику, а не общие слова

Формат по каждому источнику:

### [URL]
- Язык: [код] | Дата: [дата] | Автор/организация: [кто]
- Контекст автора: [масштаб, версии, нагрузка — при каких условиях получен опыт]

  - [факт с числом/версией]
- Оговорки самого автора: [что автор сам называет слабым/непроверенным]
- Цитата (если ценная): "[оригинал]" — перевод: "[русский]"
- Чего в тексте НЕТ, хотя заголовок обещал: [...]

В конце:

```

### Сборка результатов

После завершения всех субагентов:
1. Собери ответы всех агентов
2. Пронумеруй все источники единой нумерацией [1], [2], [3]...
3. Удали дубликаты (один URL = один источник; перевод той же статьи — тот же источник)
4. Отметь пробелы — если агент не нашёл данных по направлению или языку, зафиксируй это для reach-метрики и фазы CRITIQUE
5. Отдельно выдели факты, найденные **только** в не-англоязычных источниках — это отдельная секция отчёта

## Фаза 4: SOLUTIONS — Готовые решения

Прежде чем рассуждать «как это сделать», нужно знать, **кто это уже сделал**. Эта фаза ищет готовое, разбирает его и — при `--dive` — читает исходники.

### Что считается решением

Всё, что может дать пользу:
- **OSS-репозитории** — библиотеки, сервисы, self-hosted платформы
- **SaaS / коммерческие продукты** — включая freemium и open-core
- **Инженерные кейсы** — «как мы построили X» с достаточной детализацией, чтобы повторить
- **Reference-архитектуры и шаблоны** — boilerplate, terraform-модули, docker-compose стеки, cookbook'и вендоров
- **Смежные решения** — сделанное для другой задачи, но переиспользуемое (отметить как «adjacent»)

### Объём по режимам

| Режим | Shortlist | Разобрано карточкой | Source-dive |
|-------|-----------|--------------------|-----------|
| Quick | 3–5 | 2 (сокращённая карточка) | нет |
| Standard | 6–10 | 3 | нет (`light` по флагу) |
| Deep | 10–15 | 5 | `light` — 2 лидера |
| UltraDeep | 15+ | 7+ | `deep` — 3 лидера |

`--solutions=N` перебивает число разобранных. `--solutions=0` выключает фазу целиком (только для чисто теоретических тем).

### Шаг 1: Shortlist

Паттерны запросов — **на всех языках из пула** (китайский и русский сегменты часто знают решения, которых нет в англоязычных awesome-листах):

```
X open source            /  X 开源           /  X опенсорс аналог
awesome X                /  X 推荐 工具       /  чем заменить X
self-hosted X            /  X 自建           /  self-hosted X опыт
X alternative to Y       /  X 替代 Y         /  аналог Y без вендора
how we built X           /  我们如何实现 X     /  как мы сделали X
best X tool 2026         /  2026 X 最佳实践   /  лучший инструмент для X
X github stars           /  X github 对比     /  X на github сравнение
```

Плюс каталоги: GitHub Topics/Trending, awesome-*, Product Hunt, AlternativeTo, LibHunt, Gitee (китайский OSS), OpenAlternative.

Вывод шага — таблица-лонглист:

```
| # | Решение | Тип | URL | Почему в списке | Первичный вердикт |
|---|---------|-----|-----|-----------------|-------------------|
| 1 | ... | OSS | ... | ... | разбирать / отбросить: причина |
```

Отброшенные — с явной причиной (мёртвый, не тот масштаб, несовместимая лицензия, платно от $X). Молча выкидывать нельзя.

### Шаг 2: Карточка решения

Для каждого решения из шортлиста, помеченного «разбирать»:

```markdown
### [Название] — [одна строка: что это]

- **Тип**: OSS / SaaS / open-core / кейс / шаблон / adjacent
- **URL**: репозиторий + сайт + docs
- **Что умеет**: [3–5 пунктов по существу задачи из фазы SCOPE]
- **Стек**: язык, БД, рантайм, зависимости-тяжеловесы
- **Лицензия**: [точное название] — [что она разрешает в нашем случае]
- **Зрелость**: последний коммит [дата] | релизов за год [N] | звёзд [N] |
  открытых issues [N] (из них старше года [N]) | контрибьюторов [N] | bus factor [оценка]
- **Кто в проде**: [named users с источником, не «используется многими»]
- **Цена**: [self-host бесплатно / $X за Y / скрытая цена: инфраструктура, поддержка]
- **Порог входа**: [что нужно уметь и сколько времени до первого результата]
- **Чем НЕ подходит**: [обязательный пункт — если пусто, значит плохо искал]
- **Что можно утащить**: [даже если решение не берём: идея, алгоритм, схема данных, модуль]
- **Надёжность оценки**: [насколько это по докам, а насколько по чужому опыту / коду]
```

**Правило проверки заявлений:** README — это маркетинг. Каждое ключевое заявление («масштабируется», «production-ready», «zero-config») сверяется с issues, changelog и чужими отзывами. Расхождение README и реальности — само по себе находка, пиши её.

### Шаг 3: Source-dive — чтение исходников

Уровень задаётся `--dive` и переопределяется в диалоге («залезь в код glue-слоя», «хватит README»).

| Уровень | Что делает | Инструменты |
|---------|-----------|-------------|
| `off` | Ничего, только карточка по докам | — |
| `light` | README + дерево файлов + 1–2 ключевых файла | WebFetch (`raw.githubusercontent.com`, `github.com/.../blob/...`) |
| `deep` | Shallow clone в scratchpad + навигация по коду | Bash (`git clone --depth 1`), Grep, Read, Glob |

**Порядок работы `deep`:**

1. `git clone --depth 1 <repo>` **только** в scratchpad-каталог текущей сессии — никогда в рабочий проект
2. Карта репозитория: точка входа, структура модулей, размер (`тыс. строк`), тесты есть/нет
3. Найди **место, где решена именно наша задача** из фазы SCOPE (Grep по терминам домена) — это главная цель, а не общий обзор
4. Прочитай 3–5 ключевых файлов
5. Зафиксируй: подход, структуры данных, внешние зависимости этого участка, обработка ошибок и краевых случаев
6. Удали клон после разбора

**Формат вывода source-dive:**

```markdown
#### Разбор кода: [Название]

- **Размер**: [N] тыс. строк, [язык], тесты: [есть/нет/покрытие]
- **Точка входа**: `path/to/file`
- **Ключевые модули**:
  - `path/module_a` — [ответственность]
  - `path/module_b` — [ответственность]
- **Как решена НАША задача**: `path/file:line` — [описание подхода]
  ```[язык]
  [минимальный показательный фрагмент]
  ```
- **Структуры данных / схема**: [ключевые сущности и связи]
- **Что решено умно**: [приём, который стоит перенять]
- **Что решено плохо / хрупко**: [долги, хардкод, отсутствующая обработка ошибок]
- **Насколько реально форкнуть**: [оценка: связность, зависимости, читаемость, документированность]
```

Для агента используй тип `general-purpose` (нужны Bash/Read/Grep) с промптом по этому формату. Один агент = одно решение.

### Шаг 4: Матрица сравнения

По критериям из фазы SCOPE:

```markdown
| Критерий | Решение A | Решение B | Решение C | Своя реализация |
|----------|-----------|-----------|-----------|-----------------|
| [критерий 1] | ... | ... | ... | ... |
| Лицензия | ... | ... | ... | — |
| Зрелость | ... | ... | ... | — |
| Цена/год | ... | ... | ... | [оценка часов] |
```

Колонка «Своя реализация» обязательна — без неё нельзя сравнить build и buy.

### Шаг 5: Reach-метрика покрытия

Правило **no silent caps**: всё, что урезано, названо явно. Умолчание об урезании читается как «покрыли всё».

```markdown
## Покрытие исследования

| Ось | Покрыто | Из возможного | Не покрыто и почему |
|-----|---------|---------------|---------------------|
| Языки | en, ru, zh | + ja, de, ko, es | ja/de — не запускались (режим Standard) |
| Типов источников | docs, GitHub, форум, кейс | + paper, бенчмарк | академики не искались — тема прикладная |
| Источников найдено | [N] | — | — |
| Источников прочитано целиком | [M] из [N] | — | остальные — только сниппет/заголовок |
| Решений в лонглисте | [N] | — | — |
| Решений разобрано карточкой | [M] | — | [почему остальные отброшены] |
| Решений с прочитанным кодом | [K] | — | dive=[уровень] |
| Направления без результата | [список] | — | [что искали и не нашли] |
```

## Фаза 5: EVALUATE — Оценка (Standard+)

### Оценка надёжности каждого источника

Присвой каждому источнику балл по шкале:

| Тип источника | Диапазон | Пример |
|---------------|----------|--------|
| Официальная документация | 90-100 | docs.docker.com, nodejs.org/docs |
| Peer-reviewed / академическая статья | 85-95 | arXiv, IEEE, ACM |
| Исходный код решения (прочитан) | 85-95 | сам код — первоисточник поведения |
| GitHub (maintainer, official repo) | 75-90 | Issues от core team, README |
| Инженерный блог компании (named case) | 65-85 | Kakao Tech, Zhihu-разбор от команды |
| Авторитетный блог (автор — эксперт) | 60-80 | Blog CTO компании, ThoughtWorks |
| Stack Overflow (принятый ответ, >10 голосов) | 50-70 | Проверенные решения |
| Обычный блог / Medium / Dev.to / Habr-пост | 40-60 | Без верификации |
| Reddit / форум / Zhihu-ответ без доказательств | 20-40 | Мнения без ссылок |
| Маркетинговая страница вендора | 15-35 | Landing, «why us» |

Корректировки балла:
- **Дата >2 лет назад**: −10
- **Подтверждено 2+ источниками**: +10
- **Подтверждено источниками на разных языках**: +15 (независимые сообщества — сильный сигнал)
- **Прочитан целиком, а не по сниппету**: +5
- **Противоречит большинству**: −15 (но сохрани — может быть ценным)
- **Только сниппет, текст не читался**: −10
- **Машинный перевод без сверки с оригиналом**: −5, помечай

### Для каждого источника зафиксируй

```
[N] Название — URL
    Тип: docs | Язык: zh | Надёжность: 95 | Дата: 2026-03 | Прочитан: целиком
    Факты: ...
```

### В отчёт добавь таблицу источников

```markdown
## Источники
| # | Название | Язык | Тип | Надёжность | Дата | Прочитан | URL |
|---|---------|------|-----|-----------|------|----------|-----|
| [1] | ... | en | docs | 95 | 2026-03 | целиком | ... |
| [2] | ... | zh | блог | 55 | 2025-06 | сниппет | ... |
```

Источники с надёжностью <40 — пометь ⚠️ и не используй как единственное основание для выводов.

## Фаза 6: SYNTHESIZE — Синтез

Объедини все данные в связный анализ:
- Группировка по темам/аспектам
- Выявление паттернов и противоречий
- Каждое утверждение — со ссылкой на источник [N]
- **Готовые решения — часть синтеза, а не приложение**: выводы опираются на то, как задачу решили другие, включая прочитанный код
- **Расхождения между языковыми сообществами** — отдельно: если китайские источники хвалят то, что англоязычные ругают, это находка, а не шум. Ищи причину (масштаб, цена, доступность инфраструктуры, регуляторика)

### Обязательный блок: Build vs Buy vs Fork

Вывод формулируется явно, одним из четырёх вердиктов:

| Вердикт | Когда | Что писать |
|---------|-------|-----------|
| **Buy / взять готовое** | решение закрывает ≥80% требований, лицензия и цена ок | какое именно, что доплатить/донастроить, что потеряем |
| **Fork / допилить** | база хорошая, но 20–50% надо менять; код читаемый (по source-dive) | что форкнуть, какие модули менять, цена поддержки форка |
| **Build с переиспользованием идей** | готовое не подходит, но подходы разобраны | какие идеи и схемы данных берём, из какого решения, оценка трудозатрат |
| **Build с нуля** | ничего близкого нет, и это доказано лонглистом | почему ничего не подошло — по каждому кандидату из лонглиста |

Вердикт «Build с нуля» без разобранного лонглиста запрещён — это не вывод, а отсутствие поиска.

## Фаза 7: CRITIQUE — Критика (Deep+)

Проверь свои выводы от лица трёх ролей. Для каждой роли — ответь на ВСЕ вопросы чек-листа.

### Роль 1: Скептик-практик
- [ ] Есть ли реальные примеры использования в продакшне?
- [ ] Какие подводные камни не упомянуты?
- [ ] Масштабируется ли решение? При какой нагрузке ломается?
- [ ] Какова реальная стоимость владения (TCO), а не только цена лицензии?
- [ ] Есть ли vendor lock-in?

### Роль 2: Адвокат дьявола
- [ ] Какие аргументы ПРОТИВ основной рекомендации?
- [ ] Какой альтернативный подход мог бы быть лучше?
- [ ] Не базируется ли вывод на единственном источнике?
- [ ] Нет ли confirmation bias — искал ли я данные ПРОТИВ своей гипотезы?
- [ ] Что изменится через 1-2 года? Рекомендация устареет?

### Роль 3: Критик покрытия
- [ ] Какие языки не запускались — могло ли там быть решение, которого нет в англоязычном поле?
- [ ] Какие типы решений пропущены (SaaS? adjacent? вендорский шаблон?)
- [ ] Сколько источников прочитано целиком, а сколько взято по сниппетам — не стоит ли ключевой вывод на сниппете?
- [ ] Есть ли решение, отброшенное на лонглисте без нормальной причины?
- [ ] Если вердикт «Build с нуля» — он действительно доказан, или лонглист был поверхностным?

### Формат вывода критики

```
### Критика
**Скептик**: [находки — что слабо, что не проверено]
**Адвокат дьявола**: [контраргументы — что против]
**Критик покрытия**: [дыры в reach: языки, типы решений, непрочитанное]
**Критические пробелы**: [что нужно доискать]
**Вердикт**: пробелов нет / найдены пробелы → loop-back
```

### Протокол Loop-Back

Если найден критический пробел (вывод без достаточных источников, пропущена альтернатива, не запущен язык, где решение вероятно):
1. Сформулируй **delta-query** — конкретный поисковый запрос ТОЛЬКО по пробелу, на нужном языке
2. Выполни 1–3 WebSearch по delta-query (либо 1 точечный агент, если пробел широкий)
3. Интегрируй новые данные в выводы и обнови reach-метрику
4. Повтори критику ТОЛЬКО по закрытому пробелу

**Максимум 2 итерации loop-back.** Если после 2 итераций пробел остался — зафиксируй его в секции "Ограничения" отчёта.

## Фаза 9: RED TEAM — Стресс-тест (UltraDeep)

Четыре персоны проверяют финальный отчёт. Каждая пишет свой вердикт.

### Персона 1: Скептик
**Вопрос**: "Что может НЕ работать? Какие риски замолчаны?"
- Проверяет: технические риски, edge cases, failure modes
- Вердикт: `✅ рисков не нашёл` / `⚠️ найдены риски: [список]`

### Персона 2: Критик
**Вопрос**: "Где confirmation bias? Какие альтернативы не рассмотрены?"
- Проверяет: полноту рассмотрения, пропущенные альтернативы, однобокость
- Вердикт: `✅ анализ сбалансирован` / `⚠️ пропущено: [список]`

### Персона 3: Практик
**Вопрос**: "Как это конкретно применить в нашем стеке и контексте?"
- Проверяет: применимость к проектам пользователя, конкретность шагов
- Вердикт: `✅ готово к применению` / `⚠️ нужна адаптация: [что именно]`

### Персона 4: Инженер по внедрению
**Вопрос**: "Если я завтра беру рекомендованное решение — где я застряну?"
- Проверяет: реальность порога входа, скрытые зависимости, миграцию данных, откат, эксплуатацию и обновления, кто это поддерживает через год
- Вердикт: `✅ внедряемо` / `⚠️ блокеры внедрения: [список]`

## Правила

### Исследование
- **НИКОГДА не редактируй существующие файлы проекта** — только исследуй и создавай отчёты
- Каждое фактическое утверждение — со ссылкой на источник [N]
- Запрещено: выдуманные ссылки, placeholder-ы, утверждения без источника
- Отчёт ≥80% проза, не буллеты
- Рекомендации конкретные ("используйте X потому что Y"), не абстрактные ("рассмотрите возможность")
- Если тема про код/архитектуру ЭТОГО проекта — перенаправь на `/research`

### Готовые решения
- Вердикт «писать с нуля» **без разобранного лонглиста запрещён**
- README — маркетинг: ключевые заявления сверяй с issues, changelog, чужим опытом
- Лицензия проверяется всегда и называется точно. AGPL / SSPL / BUSL / «source-available» — красный флаг для коммерческого использования, пиши это явно
- Решение без коммитов >12 месяцев — ⚠️ «мёртвое», не рекомендовать без оговорок про поддержку форка
- У каждого решения обязателен пункт «Чем НЕ подходит». Пустой пункт = плохо искал
- Отброшенное на лонглисте — всегда с причиной, молча не выкидывать

### Source-dive
- Клонировать **только** в scratchpad-каталог текущей сессии, никогда в рабочий проект и никогда без `--depth 1`
- После разбора клон удалить
- Не запускать код из клонированных репозиториев — только чтение
- Не устанавливать зависимости незнакомых проектов
- Ссылки на код — в формате `path/file:line`, чтобы можно было проверить
- Читать код с целью «как решена наша задача», а не «пересказать репозиторий»

### Языки
- Переводить **смысл и нативную терминологию**, не слова
- Каждый источник помечен языком; цитаты — оригинал + перевод на русский
- Машинный перевод без сверки с оригиналом помечать явно
- Совпадение выводов на независимых языковых сообществах — усиливает вывод; расхождение — повод искать причину, а не игнорировать

### Покрытие
- **No silent caps**: любое урезание (топ-N, непрочитанные источники, незапущенный язык, отброшенное решение) фиксируется в reach-метрике
- Кэп параллельных агентов по режиму соблюдается; >20 — только по явной просьбе пользователя
