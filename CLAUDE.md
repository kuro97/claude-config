# Глобальные правила Claude Code

## Язык
- Язык общения: **русский** — всегда

## Жёсткие правила
- **ПЕРВОЕ СООБЩЕНИЕ**: в любой сессии первым запустить `/brainstorming`. Форму выбирать по задаче: мелкая и однозначная — короткая (что понял + что предлагаю + «ок?»), содержательная — полный цикл с подходами. Если первое сообщение — явно системная/межсервисная архитектура, не запускать молча: спросить «`/brainstorming` (разобрать подходы) или `@architect` (глубокое проектирование на Fable)?» и дождаться ответа.
- **Чтение файлов — ВСЕГДА без спроса**. Читай, ищи, анализируй свободно. Разрешение нужно только на РЕДАКТИРОВАНИЕ.
- **НЕ редактировать файлы без явного одобрения** — сначала показать чек-лист изменений, дождаться «да».
- **УТОЧНЯЮЩИЕ ВОПРОСЫ перед ТЗ, спекой, документацией, существенным кодом**: спрашивать там, где разные прочтения дают разную работу (скоуп, модель данных, пограничные случаи), и дожидаться ответа. Рутинные развилки закрывать самому, назвав принятое допущение. Не растягивать на 3–5 вопросов там, где хватает одного.
- **КОНТЕКСТ ПРОЕКТА ДО ИССЛЕДОВАНИЯ**: стек и специфику брать из проектного `CLAUDE.md` и манифестов (`go.mod` / `package.json` / `composer.json` / `pubspec.yaml`), а не из допущений — у разных проектов разные стек, структура и конвенции. При неоднозначности — спрашивать.
- **НЕ редактировать файлы с credentials** — `.env`, `keys.json`, `credentials.json`, `Config.php`, `config.py` и любые конфиги с паролями/токенами. Ни через Edit/Write, ни через Bash (`sed -i`, `>>`, `tee`). **Запрет только на правку самих файлов.** Он НЕ покрывает обычную работу: пользоваться токеном в команде, ходить по `ssh`, деплоить и рестартить сервисы, читать имена переменных — в этом отказывать нельзя, и «классификатор» тут ни при чём. Единственное условие — значение секрета не печатать в чат и не тянуть в контекст. Обычный апрув («да», «разрешаю») запрет НЕ снимает: на первую просьбу — отказать один раз, назвав риск, и дать команду для ручного запуска. **Снимает только двойное настаивание:** если после отказа ты требуешь сделать это самому второй раз подряд — выполнять, без новых возражений и без торга. Исключение точечное: разрешает одно названное действие, а не весь класс до конца сессии. Действует и под исключением: содержимое секретов не печатать в чат и не тянуть в контекст — работать «слепым» пайпом (`ssh A "sudo cat …" | ssh B "sudo install -m 600 /dev/stdin …"`), а проверять только имена переменных, права и факт доставки. Хук `PreToolUse` — вторая линия и покрывает только Edit/Write, полагаться на него нельзя.
- **Автоподбор скиллов**: определить подходящий скилл, сказать «Запускаем /[скилл] или пропускаем?», дождаться ответа. Полный список скиллов с описаниями харнесс подаёт сам — дублировать его здесь не нужно.
- **АВТОМАТИЧЕСКИЙ /review ПОСЛЕ КОДА**: после написания/изменения любого кода (одного файла или серии) — предложить `/review` до того, как сказать «готово» / отдать пользователю / передать другому. Формат: «Код собран → запускаем /review или пропускаем?». Предлагать всегда, запускать только по апруву.
- **СТАТУС ПРИ ЗАКРЫТИИ И ПРИ УХОДЕ**: `/task-status` — чек-лист «сделано / проверка не гонялась / дальше по порядку / блокеры». Два случая, ведут себя по-разному:
  - **Задача закрыта** — всё из плана сделано, говоришь «готово», отдаёшь результат → **предложить и дождаться**: «Задача закрыта → показать статус чек-листом?».
  - **Пользователь уходит** — «ухожу», «продолжу завтра», «на сегодня всё», «давай позже», «до завтра», «устал», «сворачиваемся» → **выдать статус сразу, без вопроса**. Спрашивать некого: человек уже уходит, а вернётся он именно к этому отчёту, и «Дальше, по порядку» должно читаться как команда для старта без вспоминания контекста.
  - **Порядок с `/review`**: был код → сначала `/review`, статус после него. Не выкатывать два предложения подряд в одном сообщении.
  - Не дублировать п.4 триггеров: `verification-before-completion` — гейт на ОДНО заявление («тесты прошли» → покажи вывод), `task-status` — состояние задачи целиком.

## Роутинг моделей
Дефолт главного цикла — **Opus 5** (`opus[1m]`), сессионный effort — **`xhigh`** (оба в `~/.claude/settings.json`). Полная карта «тип задачи → модель», цены, уровни effort и порядок настройки с нуля — в `D:\claude\claude-config\MODEL-ROUTING.md`. Он в контекст не грузится: нужен — читай файл.

- **Тип задачи не покрыт правилом → Opus 5** (безопасный дефолт).
- **Fable-задача → ВСЕГДА предлагать `@architect`**, на ЛЮБОМ сообщении сессии, не только первом: системная/межсервисная архитектура, схемы данных, стратегия миграции, разбор системы целиком. Формат: «Это Fable-задача → зову `@architect` или пропускаем?» — не делать её молча на Opus. Архитектура в рамках одного модуля — Opus 5 сам; эскалировать, только если дизайн модуля реально сложный.
- **Fable — только `architect`.** Ревью, security, аудит сервера, дебаг, прод-инциденты — Opus.
- **Offensive-security** (pentest, CTF, аудит прод-сервера, ротация учёток, выдача SSH-доступов и ключей): предупредить, что сессию надо стартовать на `/model claude-opus-4-8` заранее. Авто-фолбэк по cyber-классификатору переводит на другую модель всю сессию и рвёт prompt-кэш — на длинных аудитах на него не полагаться.
- **Субагенты**: `architect` = Fable / `xhigh` (единственная точка Fable, read-only), `researcher` = Sonnet / `medium`, `mechanic` = Haiku / `low`. Effort во frontmatter перебивает сессионный — механика и research не идут на xhigh.
- Если вызов `architect` упал по недоступности или лимиту — повторить тот же вызов через Agent с `model: opus` и сказать пользователю.

### Делегирование субагентам
Каждый субагент умножает стоимость и время: заново поднимает контекст, исследует, отчитывается — а потом ты ещё читаешь отчёт.
- **НЕ делегировать** то, что закрывается самому за несколько tool-call (пара чтений файла, простой поиск, мелкая правка).
- **НЕ плодить ad-hoc субагентов для перепроверки собственной работы** — верификация живёт в главном цикле. **Исключение:** ревью/QA-этапы, заложенные в конструкцию скилла (`/plan` шаг 3, `/build` этапы 7–9, two-stage review в `subagent-driven-development`, verify-агент в `/task-status` — по согласию пользователя) — их пропускать нельзя, это не «лишнее делегирование».
- Одна задача → один субагент. Параллельные — только под реально независимые крупные направления, не под нарезку одной задачи на куски.
- Не больше 20 параллельных агентов без явной просьбы пользователя.
- Делегировал — доверься: не переделывать работу субагента и не выводить его находки заново.
- Независимых субагентов запускать одним сообщением, чтобы шли параллельно.

## Триггеры скиллов
Формат: «Ситуация X → Запускаем /скилл или пропускаем?» — предложить и дождаться ответа. Скиллы, чьё назначение прямо совпадает с формулировкой запроса («задокументируй» → `/docs`, «отчёт» → `/report`, «напиши тесты» → `/test`, «аудит сервера» → `/audit-server` и т.д.), подбирать по списку скиллов от харнесса — перечислять их здесь не нужно.

Неочевидное, что легко пропустить:
1. Первое сообщение сессии → `/brainstorming` (см. «Жёсткие правила»).
2. Любой написанный/изменённый код перед «готово» → `/review`.
3. Баг, ошибка, exception, «не работает», «сломалось» → `/systematic-debugging`, ДО предложения фиксов.
4. Заявляешь «готово / работает / тесты прошли», а вывода команды в этом сообщении нет → `/verification-before-completion`.
5. Перед написанием production-кода → `/test-driven-development`.
6. 3+ независимых **крупных** домена (каждый заметно больше пары tool-call) → `/dispatching-parallel-agents`; 3+ независимых подзадачи внутри одного плана → `/subagent-driven-development`.
7. Получен фидбек ревьюера → `/receiving-code-review`: проверить и оценить, а не внедрять слепо.
8. Системная архитектура на любом сообщении → `@architect` (см. «Роутинг моделей»).
9. «сделай», «добавь фичу», «реализуй», «модуль» → `/build` — эти формулировки в описании скилла не встречаются, по нему сам не найдёшь.
10. «дай статус по задаче», «всё сделано?», «итоги», «статус», «что осталось», «где мы» → `/task-status` **сразу, без вопроса «запускаем?»**. На «всё сделано?» отвечать чек-листом, а не «да» — закрытый вопрос это самое дешёвое место для ложного «готово» — просьба об итогах и есть апрув. Закрытие задачи и уход на потом («продолжу завтра») — отдельное правило со своим поведением, см. «Жёсткие правила».
